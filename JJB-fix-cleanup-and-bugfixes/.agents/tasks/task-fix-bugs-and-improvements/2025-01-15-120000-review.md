# Gameplay polish: team-colored fists, alternating punches, auto-fire, weapon physics, and UX fixes

This change adds several gameplay improvements to a Three.js prison FPS game: guard fists now render dark blue sleeves (prisoners keep orange), punch animations alternate between left and right hands, automatic weapons fire continuously while the mouse is held, dropped weapons have physics (gravity, floor/wall collisions, throw velocity), and the inventory closes when a slot is clicked. A terminal highlight intensity fix makes the interaction glow actually visible.

Watch for: the weapon drop physics uses per-frame `setFromObject` and iterates all map colliders for each dropped weapon each tick — with many weapons on the ground this becomes O(weapons * colliders) per frame (confirmed). The `PlaytestMode` hands constructor does not pass the `team` parameter, so playtest mode always shows the default (prisoner) sleeves regardless of selected team (confirmed).

## High-level view

Team-colored sleeves are threaded through `Hands`, `Weapon`, and `Combat` via a `team` parameter. `Game.ts` recreates both hands and combat with the correct team on selection. However, `PlaytestMode.ts` creates `new Hands()` without forwarding its own `team` argument, so the fix is incomplete in editor playtest mode.

Weapon drop physics apply gravity, floor collision, and per-axis wall collision against `mapColliders`. The implementation constructs a new `Box3` via `setFromObject` for every axis check every frame per weapon, triggering world matrix updates and geometry bounding recomputation. For 1-3 dropped weapons this is fine; at scale it would need pooling.

The weapon pickup uses 3D `distanceTo` with a 2-unit range. Since the camera sits at y=1.7 and grounded weapons at y=0.1, the vertical gap alone consumes 1.6 units, leaving only ~1.2 units of horizontal reach (via Pythagorean). This makes pickup feel tight and could allow through-floor pickup if multi-level geometry is added.

1. **PlaytestMode ignores team for hands** — `PlaytestMode` constructs `new Hands()` without passing `team`, so editor playtest always shows prisoner-colored sleeves. Pass the `team` argument through.
2. **O(weapons * colliders) per frame for drop physics** — Each in-flight weapon calls `setFromObject` and iterates all colliders twice per frame (X and Z axes). Pool the bounding box or cache it per weapon to avoid redundant geometry traversal.
3. **Tight pickup radius due to vertical distance** — `tryPickupWeapon` uses 3D `distanceTo` with a 2-unit range. The 1.6-unit vertical gap between camera and grounded weapon leaves little horizontal leeway. Consider using XZ-only distance or increasing the range.
4. **No collision check for weapon pickup at height** — Conversely, a weapon on a ledge could be picked up through a floor/ceiling if multi-level maps are introduced.

## PlaytestMode team sleeve mismatch

In `PlaytestMode.ts` line 64, the hands are constructed without the team parameter:

```typescript
this.hands = new Hands(); // should be new Hands(team)
```

The `team` argument is available in the constructor scope. The `Combat` system correctly receives the team option on the next line, and `Weapon` will render team-colored hands on the gun — so when a guard equips a weapon in playtest mode, the weapon hands are navy but the bare fists are orange. This is a confirmed inconsistency.

## Weapon drop physics allocation pattern

Every frame for every non-grounded weapon, the update loop does:

```typescript
const testBoxX = new THREE.Box3().setFromObject(dropped);
testBoxX.translate(new THREE.Vector3(dropped.userData.velocityX * delta, 0, 0));
```

`setFromObject` traverses the object hierarchy, forces world matrix updates, and computes geometry bounding boxes. This happens twice per weapon per frame (once for X, once for Z). With the current game spawning at most 3-4 dropped weapons, this won't cause frame drops. But if weapons accumulate (e.g., after many deaths without cleanup), it could. A pooled `Box3` updated once per weapon per frame, then translated twice, would halve the cost.

## Weapon pickup range includes vertical distance

`tryPickupWeapon` uses `playerPos.distanceTo(droppedWeapon.position)` for the 2-unit pickup range. Since `playerPos` is the camera at y=1.7 and a grounded weapon is at y=0.1, the vertical distance alone is 1.6 units, leaving only ~1.2 units of horizontal reach. This means the player must stand almost directly on top of the weapon to pick it up. Conversely, a weapon on a ledge at y=3.7 would be within 2.0 units of a player at y=1.7 standing directly below, enabling pickup through floors if multi-level geometry exists.
